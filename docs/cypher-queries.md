# Cypher queries the application depends on

Executable implementations live in `backend/app/memory/manager.py` and `backend/app/agents/recovery.py`; these examples use the same traversal direction and parameter convention. All user values are parameters. Label/index identifiers are fixed server constants.

## Readiness

```cypher
MATCH (r:AgentRun {id:$run})-[:HAS_STEP]->(s:Step)
OPTIONAL MATCH (s)-[:DEPENDS_ON]->(d:Step)
WITH r,s,collect(d) AS deps
WHERE r.status='running'
  AND s.status IN ['pending','ready','retryable']
  AND s.retry_after_ms <= $now
  AND s.attempt_count < s.max_attempts
  AND s.lease_until_ms <= $now
  AND all(d IN deps WHERE d.status='succeeded' AND d.verification_status='passed')
OPTIONAL MATCH (s)-[:TARGETS]->(resource:Resource)
WITH s,deps,collect(resource) AS resources
WHERE all(resource IN resources WHERE resource.available=true)
RETURN s,deps ORDER BY s.priority DESC,s.created_at LIMIT 30
```

The atomic claim repeats this predicate inside the write query, filters `s.id=$step`, increments `attempt_count`, sets the lease, creates an Attempt with a new token, and records assignment and decision evidence. Reading ready tasks alone never reserves a task. Concurrent claims are tested with two independently connected workers.

## Dependency impact and reverse revalidation

```cypher
MATCH p=(affected:Step)-[:DEPENDS_ON*1..30]->(s:Step {id:$id})
RETURN affected,nodes(p) LIMIT 300
```

Returns the actual path for each affected task; one hop means directly blocked. Completed tasks outside these paths remain unaffected. Independent ready steps use the readiness query above. The privileged invalidate endpoint traverses the same paths and changes downstream `verification_status` to `stale`, preserving original Attempt verification records. Stale prerequisites cannot authorize further work. Automatic rebuilding of stale results is not implemented.

## Related failures and recovery

```cypher
MATCH (:Step {id:$id})-[:HAS_ATTEMPT]->(:Attempt)-[:CAUSED_FAILURE]->(f:Failure)
MATCH (related:Failure)
WHERE related.normalized_signature=f.normalized_signature
RETURN DISTINCT related ORDER BY related.discovered_at DESC LIMIT 20
```

```cypher
MATCH (p:Procedure)-[:APPLIES_TO]->(f:Failure)
WHERE f.run_id=$run
RETURN DISTINCT p ORDER BY p.verified_success_count DESC LIMIT 20
```

Recovery records a Procedure as **proposed** until the failed test step passes independent verification. The correction becomes a new Step and a DEPENDS_ON prerequisite of the failed test. Signature mismatch, patch precondition mismatch, and exhausted retry budget do not produce unconditional retries.

## Decision evidence

```cypher
MATCH (d:Decision {id:$id})
OPTIONAL MATCH (d)-[r:BASED_ON]->(e)
RETURN d,collect(e),collect(r)
```

The response includes stored rationale, source properties, and relationship paths. Scheduling events snapshot dependency IDs and their passed state at claim time; source nodes can subsequently change. Recovery choices are labeled proposed at decision time, even if the procedure is verified later. No explanation is generated by asking a model to invent a rationale after execution.

## Indexes, constraints, plans

```cypher
CREATE INDEX FOR (n:Step) ON (n.id)
CREATE INDEX FOR (n:Step) ON (n.run_id)
CREATE INDEX FOR (n:Step) ON (n.status)
CALL db.indexes()
```

Unique constraint command: `GRAPH.CONSTRAINT CREATE graph_name UNIQUE NODE Step PROPERTIES 1 id`. Syntax was checked against the running database. Python `graph.explain(query, params)` captures actual query plans. `scripts/benchmark.py` measures 50 client round trips per query and writes environment, timings, and plans to `docs/query-timings.json`. These measurements describe a small local graph and do not establish production throughput.
